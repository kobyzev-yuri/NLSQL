```sql
-- ✅ ПРАВИЛЬНО: Комментарий к полю с объяснением назначения
COMMENT ON COLUMN public.equsers.department IS 
'Ссылка на отдел пользователя. 
Связь с таблицей eq_departments через поле id.
Если NULL - пользователь не привязан к отделу.';

COMMENT ON COLUMN public.equsers.deleted IS 
'Флаг мягкого удаления (soft delete).
true - запись удалена, но сохранена в БД для истории.

ВАЖНО: Все запросы должны фильтровать deleted=false для получения активных записей.';
```

```markdown
# Описание схемы базы данных

## Таблица: equsers (Пользователи)

**Назначение:** Хранение учетных записей сотрудников системы.

**Основные поля:**
- `id` (UUID) - уникальный идентификатор пользователя
- `login` (VARCHAR) - логин для входа в систему (уникальный)
- `email` (VARCHAR) - электронная почта пользователя
- `surname`, `firstname`, `patronymic` (VARCHAR) - ФИО пользователя
- `department` (UUID) - ссылка на отдел (FK → eq_departments.id)
- `deleted` (BOOLEAN) - флаг мягкого удаления

**Бизнес-правила:**
- Удаленные пользователи (deleted=true) не должны отображаться в интерфейсе
- Пользователь обязательно должен иметь логин
- Email может быть NULL, но должен быть уникальным, если указан

**Связи:**
- `department` → `eq_departments.id` (многие к одному)
- `ownerid` → `equsers.id` (создатель записи)

## Таблица: eq_departments (Отделы)

**Назначение:** Организационная структура компании.

**Основные поля:**
- `id` (UUID) - уникальный идентификатор отдела
- `name` (VARCHAR) - наименование отдела
- `code` (VARCHAR) - код отдела (для интеграций)
- `parent_id` (UUID) - родительский отдел (иерархия)

**Бизнес-правила:**
- Отделы могут иметь иерархическую структуру (parent_id)
- Код отдела должен быть уникальным
```

## 💎 Ценность комментариев в БД

### Почему комментарии критически важны?

#### 1. **AI понимает назначение таблиц и полей**

**Пример без комментария:**
```
Таблица: equsers
Поля: id, login, department, deleted
```
→ AI не понимает, что такое `department` и как его использовать

**Пример с комментарием:**
```
Таблица: equsers (Пользователи системы)
- department: ссылка на отдел (FK → eq_departments.id)
- deleted: флаг мягкого удаления (фильтровать deleted=false)
```
→ AI понимает структуру и бизнес-логику

#### 2. **AI генерирует более точные SQL запросы**

**Без комментариев:**
```sql
-- AI может сгенерировать:
SELECT * FROM equsers WHERE department = 'IT';
-- ❌ Ошибка: department - это UUID, а не строка
```

**С комментариями:**
```sql
-- AI понимает и генерирует правильно:
SELECT u.*, d.name as department_name 
FROM equsers u 
JOIN eq_departments d ON u.department = d.id 
WHERE d.name = 'IT' AND u.deleted = false;
-- ✅ Правильно: JOIN с таблицей отделов
```

#### 3. **AI понимает бизнес-правила**

**Пример комментария с бизнес-правилом:**
```sql
COMMENT ON COLUMN public.equsers.deleted IS 
'Флаг мягкого удаления.
ВАЖНО: Все запросы должны включать условие deleted=false для получения только активных записей.
Удаленные записи сохраняются для истории, но не должны отображаться пользователям.';
```

→ AI автоматически добавляет `WHERE deleted = false` в запросы

#### 4. **AI понимает связи между таблицами**

**Пример с описанием связей:**
```sql
COMMENT ON TABLE public.tbl_incoming_payments IS 
'Входящие платежи.
- principal_assignment_id: ссылка на поручение (FK → tbl_principal_assignment.id)
- payment_date: дата поступления платежа
- debit/credit: дебет/кредит платежа
- client_inn: ИНН клиента (для связи с tbl_business_unit)';
```

→ AI понимает, как делать JOIN между таблицами

## 📝 Примеры правильной подготовки

### Пример 1: Таблица пользователей

#### ❌ ПЛОХО (текущее состояние):
```sql
CREATE TABLE public.equsers (
    id uuid DEFAULT uuid_generate_v4() NOT NULL,
    login character varying(100),
    department uuid,
    deleted boolean DEFAULT false
);
-- Нет комментариев!
```

#### ✅ ХОРОШО (рекомендуется):
```sql
CREATE TABLE public.equsers (
    id uuid DEFAULT uuid_generate_v4() NOT NULL,
    login character varying(100),
    department uuid,
    deleted boolean DEFAULT false
);

-- Комментарий к таблице
COMMENT ON TABLE public.equsers IS 
'Таблица пользователей системы DocStructure.
Содержит учетные записи сотрудников с их контактными данными и правами доступа.

Основные поля:
- id: уникальный идентификатор (UUID)
- login: логин для входа (обязателен, уникален)
- email: электронная почта (может быть NULL)
- department: ссылка на отдел (FK → eq_departments.id)
- deleted: флаг мягкого удаления

Бизнес-правила:
- Все запросы должны фильтровать deleted=false для получения активных пользователей
- Пользователь должен иметь уникальный логин
- Email должен быть уникальным, если указан

Связи:
- department → eq_departments.id (многие пользователи к одному отделу)
- ownerid → equsers.id (создатель записи)';

-- Комментарии к ключевым полям
COMMENT ON COLUMN public.equsers.department IS 
'Ссылка на отдел пользователя.
Связь с таблицей eq_departments через поле id.
Если NULL - пользователь не привязан к отделу.
Для получения названия отдела используйте JOIN: 
  JOIN eq_departments d ON u.department = d.id';

COMMENT ON COLUMN public.equsers.deleted IS 
'Флаг мягкого удаления (soft delete).
true - запись удалена, но сохранена в БД для истории
false - активная запись
КРИТИЧЕСКИ ВАЖНО: Все SELECT запросы должны включать WHERE deleted=false';
```

### Пример 2: Таблица платежей

#### ❌ ПЛОХО (текущее состояние):
```sql
CREATE TABLE public.tbl_incoming_payments (
    id uuid DEFAULT uuid_generate_v4() NOT NULL,
    payment_date timestamp without time zone,
    debit double precision,
    credit double precision,
    client_inn character varying(255),
    principal_assignment_id uuid
);
-- Нет комментариев!
```

#### ✅ ХОРОШО (рекомендуется):
```sql
CREATE TABLE public.tbl_incoming_payments (
    id uuid DEFAULT uuid_generate_v4() NOT NULL,
    payment_date timestamp without time zone,
    debit double precision,
    credit double precision,
    client_inn character varying(255),
    principal_assignment_id uuid,
    has_nds boolean
);

COMMENT ON TABLE public.tbl_incoming_payments IS 
'Таблица входящих платежей.
Содержит информацию о платежах, поступивших от клиентов.

Основные поля:
- payment_date: дата поступления платежа
- debit: дебет (сумма поступления)
- credit: кредит (сумма списания)
- client_inn: ИНН клиента (для связи с tbl_business_unit)
- principal_assignment_id: ссылка на поручение (FK → tbl_principal_assignment.id)
- has_nds: флаг наличия НДС в платеже

Бизнес-правила:
- Платеж должен иметь либо debit, либо credit (не оба одновременно)
- Если указан client_inn, можно найти клиента через tbl_business_unit.inn
- Если указан principal_assignment_id, платеж связан с поручением

Использование:
- Для поиска платежей клиента: WHERE client_inn = ?
- Для фильтрации по дате: WHERE payment_date >= ? AND payment_date < ?
- Для исключения удаленных: WHERE deleted = false';

COMMENT ON COLUMN public.tbl_incoming_payments.principal_assignment_id IS 
'Ссылка на поручение (principal assignment).
Если указан, платеж связан с конкретным поручением.
Для получения данных поручения используйте JOIN:
  JOIN tbl_principal_assignment pa ON ip.principal_assignment_id = pa.id';

COMMENT ON COLUMN public.tbl_incoming_payments.has_nds IS 
'Флаг наличия НДС в платеже.
true - НДС включен в сумму платежа
false - НДС не включен
Используется для расчета налоговой отчетности и формирования проводок.';
```


### Шаг 2: Создать дамп БД с комментариями

```bash
pg_dump -h localhost -U postgres -d test_docstructure \
  --schema-only --no-owner --no-privileges \
  > schema_with_comments.sql
```

### Шаг 3: Перезагрузить векторную базу знаний

После добавления комментариев необходимо:
1. Обновить DDL в векторной базе (если используется автоматический ингест)
2. Перегенерировать эмбеддинги
