## Интеграционный датафлоу: кто за что отвечает

Этот документ фиксирует конечный поток данных и разграничение ответственности между нашей системой NL→SQL и системами клиента.

### 1) Общая схема потока

1. Пользователь (клиентская сторона) формулирует запрос на естественном языке
   - Каналы ввода: Web/Telegram/иные интерфейсы клиента
2. Клиентская интеграция отправляет запрос в наш Core API
   - POST `http://<core_api>:8000/query` или `/query/execute`
3. Наш Core API формирует SQL (NL→SQL) с учётом домена и контекста (RAG)
4. (Опционально) Выполнение SQL: вызывается API клиента (в проде) или MOCK API (в разработке)
5. Результаты возвращаются в клиентский интерфейс

### 2) Ответственность нашей команды (мы)

- Core API (FastAPI, `src/api/main.py`)
  - Эндпоинты `/query`, `/query/execute`, `/test-search`, `/training/*`, `/health`
  - Сервис `QueryService` (генерация SQL, RAG-контекст)
- Логика генерации SQL (LLM)
  - `SimpleOpenAISQL` (прямой GPT-4o/ProxyAPI)
  - Пайплайны/клиенты Vanna (при необходимости):
    - `DocStructureVannaNative`, `OptimizedDualPipeline`, `EnhancedKBAgent`
  - Семантический поиск (RAG): `vanna_semantic_fixed.create_semantic_vanna_client()`
- Векторная база знаний
  - Таблица `vanna_vectors`, индексы pgvector
  - Документ `docs/VECTOR_DB.md` — структура, обучение, ретривер
  - UI обучения/диагностики: Vector KB (порт 8503)
- Документация и скрипты запуска
  - `docs/USER_GUIDE.md`, `docs/API_REFERENCE.md`, `docs/SERVICES_STARTUP_GUIDE.md`
  - `start_all_services.sh`, `run_stack.sh`, `start_vector_kb.sh`

### 3) Ответственность клиента

- Каналы ввода/интерфейсы
  - Web/Telegram/внутренние порталы клиента
  - Аутентификация/SSO, трекинг сессий и аудит пользовательских действий
- Исполнение SQL и бизнес-права
  - В продакшене: клиентский API для исполнения SQL и применения ролевых ограничений
  - В разработке/демо: MOCK API (наш) имитирует поведение
- Источники данных
  - Экспорт/доступ к прод-данным (или их обезличенным копиям)
  - Согласование схем и наполнение `vanna_vectors` (через наш UI и/или автоматические процедуры)

### 4) Точки интеграции и протоколы

- Генерация SQL: POST `/query`
  - Вход: `{ question, user_id?, role?, department?, context? }`
  - Выход: `{ sql, question, user_id }`
- Генерация и выполнение: POST `/query/execute`
  - Наш Core API вызывает API клиента (или MOCK API) для исполнения SQL
  - Выход: `{ data, columns, row_count, execution_time, sql }`
- Семантический поиск/диагностика: POST `/test-search`
- Обучение (по необходимости): `/training/example`, `/training/status`

### 5) Данные и расположение артефактов

- Поставка клиента со схемой/дампом: `data/DocStructureSchema/`
  - Путь можно задать через `DOCSTRUCTURE_DIR`
- Переменные окружения: `config.env(.example)`
- База данных: `DATABASE_URL` (PostgreSQL с расширением pgvector)

### 6) Развёртывание по окружениям

- Разработка
  - MOCK API включён, веб-интерфейсы по localhost-портам
  - Наполнение векторной БД через Vector KB/UI
- Прод
  - Заменить MOCK API на клиентский API выполнения SQL
  - Подключить клиентские каналы ввода (Web/Telegram) к `/query`/`/query/execute`
  - Включить мониторинг запросов/ошибок и аудит

### 7) SLA и границы ответственности (кратко)

- Мы: корректность генерации SQL на основе предоставленных данных/контекста; доступность Core API; консистентность векторной БД; документация и инструменты
- Клиент: доступность источников данных; исполнение SQL и применение бизнес-прав; интеграция фронтов и аутентификация
